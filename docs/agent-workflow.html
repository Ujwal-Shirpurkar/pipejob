Section A

What the Agent Does

Product view and technical view of the PipeJob automation agent.

🎯 Product View — What Problem It Solves

Job searching is repetitive and time-consuming. PipeJob automates the mechanical parts of the process while keeping the human in the loop for decisions that matter.

  • Discovers job listings from Indeed and Stepstone automatically
  • Scores each job against your master CV using Claude AI (0–100 match)
  • Generates a tailored CV and cover letter as DOCX files per job
  • Auto-fills application forms and uploads documents via browser automation
  • Enforces a daily application rate limit to avoid spam behavior (default: 5/day)
  • Provides a real-time dashboard to track all applications and their status

Human stays in control of: triggering discovery, deciding which jobs to analyse/apply, skipping bad fits, managing the master CV, and reviewing documents before submission.

⚙️ Technical View — How It Works

  • Discovery: Playwright + Stealth scrapes Indeed (CSS selectors) and Stepstone (API interception). Anti-bot: rotating user-agents, random viewports, human-like delays (2–6s), mouse simulation.
  • Analysis: Full job description + master CV sent to Claude Sonnet 4. Returns match score, required/missing keywords, tailored summary, and a cover letter draft.
  • Document Generation: docx library builds DOCX files. CV highlights required keywords in bold. Cover letter uses Claude's draft. Output goes to ./outputs/{jobId}/.
  • Submission: Playwright navigates to job URL, detects form fields by regex on name/id/placeholder, fills them, uploads DOCX files, clicks submit. Dev mode = dry run (no actual submit).
  • Persistence: SQLite stores every application's full lifecycle, status history, form fields used, match score, and file paths.
  • Rate Limiting: Redis tracks timestamps in a 24-hour rolling window. The applicationRateLimiter middleware enforces this before the apply endpoint.
  • Real-time UI: Server-Sent Events (SSE) stream from /api/jobs/stream push live updates to the frontend LiveFeed component.

Known Issues in the Current Code

Real bugs and gaps identified by reading the source — not speculation.

🐛 BUG: checkDailyLimit() called without await — rate limit check always passes

File: server/src/routes/jobs.ts:149. The call if (!checkDailyLimit()) does not await the Promise. A Promise object is always truthy, so this guard never fires. The applicationRateLimiter middleware (line 143) still works correctly, but the in-handler check is a no-op.

🐛 BUG: app.analysis is never persisted to the database

File: server/src/routes/jobs.ts:118–140. The /generate route checks if (!app.analysis) before generating documents. However, the JDAnalysis result from /analyse is only returned in the HTTP response — it is never stored in SQLite. After a server restart, getApplication(id) will return the job with analysis: undefined, making document generation impossible for any previously-analysed job. The match_score field is saved, but not the full analysis object.

🐛 BUG: discoverJobs() in API client sends location field that backend ignores

File: client/src/api/client.ts:16 sends { keywords, location, sources } but server/src/routes/jobs.ts:72 destructures only { keywords, sources }. Location is hardcoded to 'Deutschland' inside the scraper. Any location input from the frontend is silently dropped.

⚠️ GAP: Dashboard "Discover" button not wired to any UI control

File: client/src/pages/Dashboard.tsx. There is no Discover button or form in the current Dashboard component. The discoverJobs function is imported in api/client.ts but is not called from any visible UI component. Discovery can only be triggered via direct API call.

⚠️ GAP: LinkedIn source declared but not implemented

File: server/src/types/index.ts. The source union type includes 'linkedin', but there is no linkedin.ts scraper file. Passing sources: ["linkedin"] to the discover endpoint will silently return no results.

⚠️ GAP: pdf-lib and bull are installed but unused

pdf-lib is in server/package.json but no code imports or uses it — documents are DOCX only. bull (Redis job queue) is installed but no queue is configured or used. These are dead weight dependencies.

High-Risk Areas

Areas most likely to break or cause incorrect behavior in production.

Critical

Analysis not persisted to DB

After a server restart, any job in 'analysed' status cannot proceed to document generation. app.analysis is always undefined when retrieved from DB. The generate endpoint will always return 400 for previously-analysed jobs after a restart.

Critical

Rate limit in-handler check is broken

checkDailyLimit() is called without await on line 149. This means the secondary check inside the apply handler is effectively disabled. Only the middleware check (line 143) actually enforces the limit.

High

Scraper DOM / API structure fragility

Indeed uses CSS class selectors ([class*="jobTitle"]) that change frequently. Stepstone relies on intercepting an undocumented internal API. Either scraper could silently return 0 results after a platform update, with no alerting.

High

Form filler regex matching is brittle

The form auto-fill relies on regex pattern matching against field attributes. Non-standard field names (common in bespoke ATS systems) will be missed silently. There is no fallback for required fields that aren't filled.

Medium

POST /api/cv overwrites master-cv.json with no validation

Any JSON body is accepted and written directly to master-cv.json. There is no Zod validation on the incoming CV data. Sending a partial or malformed body permanently corrupts the master CV.

Medium

Claude response JSON parsing can throw

The analyser strips markdown fences then calls JSON.parse(). If Claude returns non-JSON (e.g., an error message, partial response), the parse throws and the job is marked as 'error'. No retry logic exists.

Medium

No input sanitization on rawJD stored in DB

Raw HTML/text scraped from job listings is stored directly in SQLite and rendered in the frontend via <pre>. While not exploitable via SQLite (uses parameterized queries), XSS vectors should be verified if rawJD is ever rendered via dangerouslySetInnerHTML.

Low

Playwright browser instance not cleaned up on error

If scraping or form-filling throws mid-execution, the browser instance may not be closed. closeBrowser() exists but is only called on clean exit. Repeated errors could leak browser processes.

Suggested Next Steps

Ordered by impact. Fix bugs first, then add test infrastructure, then expand coverage.

  • Fix: Persist JDAnalysis to SQLite Add an analysis TEXT column to the applications table. JSON-stringify before insert, JSON-parse on read. This unblocks the generate endpoint after server restarts and is the single most impactful fix.
  • Fix: Add await to checkDailyLimit() In server/src/routes/jobs.ts:149, change if (!checkDailyLimit()) to if (!await checkDailyLimit()). Low effort, fixes a real correctness bug.
  • Fix: Add Zod validation to POST /api/cv Validate the incoming MasterCV shape before writing to disk. Prevents silent data corruption from a bad POST body.
